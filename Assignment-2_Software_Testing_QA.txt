Q1. A university has developed an Online Examination Management System in
    which students can register for examinations, select subjects, make
    payments, download admit cards, and view results. Develop a complete
    testing strategy for the system by explaining how testing
    fundamentals, testing types, static testing, dynamic testing,
    verification, and validation would be applied at different stages of
    development. Justify why each testing activity is required.
--------------------------------------------------------------------------
ANSWER:

1. TESTING FUNDAMENTALS APPLIED (7 principles)
   - Testing shows presence of defects: we plan to find defects, not prove
     there are none.
   - Exhaustive testing is impossible: we use risk-based selection (payment
     and results are highest risk).
   - Early testing: requirements and design are reviewed before coding.
   - Defect clustering: payment and result-calculation modules are expected to
     have most defects, so they get extra effort.
   - Pesticide paradox: test cases are reviewed and updated every cycle.
   - Testing is context dependent: an exam system needs strong security,
     data accuracy and load testing (registration rush).
   - Absence-of-errors fallacy: a bug-free system is useless if it doesn't
     meet student/university needs, so validation is done.

2. TESTING STRATEGY BY DEVELOPMENT STAGE

   Stage 1: Requirements
     - Static testing: review SRS for ambiguity (e.g., "fast payment"),
       missing rules (last registration date, fee refund), conflicts.
     - Verification: "Are we building the product right?" - check SRS against
       university rules.
     - Why: defects found here cost the least to fix.

   Stage 2: Design
     - Static testing: review architecture, database design, UI wireframes,
       security design.
     - Verification: design traces back to requirements (traceability matrix).
     - Why: avoids rework in code and DB structure.

   Stage 3: Coding
     - Static testing: code reviews, walkthroughs, static analysis tools
       (checking coding standards, unused variables, SQL injection patterns).
     - Dynamic testing: unit testing by developers (fee calculation, grade
       function, admit card generator).
     - Why: finds logic and coding errors early.

   Stage 4: Integration
     - Dynamic testing: integration testing of Registration -> Subject
       selection -> Payment gateway -> Admit card -> Result module.
     - Why: interface and data-flow errors appear only when modules join.

   Stage 5: System testing
     - Functional testing: registration, subject selection, payment (success
       / failure / duplicate), admit card download, result viewing.
     - Non-functional testing:
         * Performance/load: thousands of students registering simultaneously.
         * Security: login, session handling, SQL injection, access control
           (student cannot see another's result), payment security.
         * Usability: ease of navigation, mobile friendliness.
         * Compatibility: Chrome, Firefox, Edge, Android, iOS.
         * Reliability/recovery: payment gateway failure, server crash.
     - Black-box techniques: EP, BVA, decision table, state transition
       (Registered -> Paid -> Admit Card Generated).
     - Why: validates the whole system against requirements and quality
       attributes.

   Stage 6: Acceptance
     - Validation: "Are we building the right product?" - university staff
       and sample students perform UAT (alpha/beta).
     - Why: confirms real-world needs are met.

   Stage 7: Maintenance
     - Regression testing after every change (e.g., fee structure change) and
       confirmation (retesting) of fixes.
     - Why: ensures new changes don't break existing features.

3. VERIFICATION VS VALIDATION SUMMARY
   Verification (static): reviews, inspections, walkthroughs, static analysis.
   Validation (dynamic): executing code in unit, integration, system, UAT.

4. ENTRY/EXIT CRITERIA AND REPORTING
   Entry: approved SRS, stable build, test environment ready.
   Exit: 100% critical test cases executed, no open Critical/Major defects,
   95% overall pass rate, requirement coverage 100%.
   Defects tracked in a tool with metrics reported weekly.

Q2. Consider an online banking application that allows users to log in,
    transfer money, add beneficiaries, pay bills, and view transaction
    history. Identify and analyze the possible defects that can be
    detected through static testing before executing the application.
    Explain how static testing can reduce the cost and effort of later
    dynamic testing.
--------------------------------------------------------------------------
ANSWER:

Static testing examines documents and code without executing the software
(reviews, walkthroughs, inspections and static code analysis).

DEFECTS DETECTABLE BY STATIC TESTING

A. Requirement defects
   - Ambiguity: "Transfers should be processed quickly" (no time given).
   - Missing: daily transfer limit, minimum balance rule, OTP validity time,
     what happens when the session expires mid-transfer.
   - Contradiction: one section says OTP is required for all transfers; another
     says only above Rs. 10,000.
   - Untestable: "System should be very secure".
   - Missing error messages for failed login/transfer.

B. Design defects
   - No account lock after repeated failed logins.
   - Passwords stored without hashing.
   - No transaction rollback design when debit succeeds but credit fails.
   - Missing audit/log design; no session timeout design.

C. Code defects (found by review or static analysis tools)
   - SQL injection vulnerabilities (string concatenation in queries).
   - Hard-coded passwords/keys.
   - Unvalidated inputs (negative transfer amount, beneficiary account number).
   - Unused variables, dead code, unreachable code.
   - Possible null pointer or divide-by-zero.
   - Resource leaks (DB connections not closed).
   - Incorrect use of float for money instead of decimal.
   - Missing exception handling in payment calls.
   - Violation of coding standards.
   - Race conditions in balance update (no locking).

D. Document defects
   - Inconsistent terminology (beneficiary vs payee).
   - Missing traceability between requirements and test cases.
   - Incomplete user manual or API specification mismatch.

HOW STATIC TESTING REDUCES COST AND EFFORT
1. Early detection: a defect found at requirement stage costs about 1 unit; in
   coding 5-10 units; in system testing 20-50 units; in production 100+
   units (cost-of-defect curve).
2. Fewer defects reach dynamic testing, so fewer test runs fail, fewer
   retests and regression cycles are needed.
3. Finds defects that are difficult to find by running tests (security
   weaknesses, dead code, standards violations).
4. Reduces debugging time: a review pinpoints the defect location directly,
   while dynamic testing only shows the failure.
5. Improves test case quality: clear, testable requirements make test case
   design easy and complete.
6. Prevents defect multiplication: wrong requirements do not propagate into
   design, code and test cases.
7. Saves rework, delays and reputational/financial loss in banking.
8. Spreads knowledge and improves developer discipline.

Conclusion: static testing is cheap, early and effective, and complements
(not replaces) dynamic testing.

Q3. A development team has submitted a module containing approximately
    2,000 lines of code for review. The module follows inconsistent
    naming conventions, contains duplicated logic, has inadequate
    comments, and uses complex conditional statements. Design a formal
    review process for this module. Include review participants,
    preparation activities, review stages, defect classification, review
    checklist, documentation, and follow-up activities.
--------------------------------------------------------------------------
ANSWER:

A formal review (Fagan-style inspection) is a structured process with defined
roles, entry/exit criteria and documented results.

1. REVIEW PARTICIPANTS
   - Moderator/Review leader : Plans, runs meeting, ensures process followed.
   - Author                  : Developer who wrote the module; answers
                               questions; does not defend.
   - Reviewers/Inspectors (2-4): Senior developer, tester, designer/architect.
   - Reader                  : Paraphrases the code in the meeting.
   - Recorder/Scribe         : Logs all defects and decisions.
   - Optional: QA representative, manager (as observer only).

2. ENTRY CRITERIA
   - Code compiles without errors, passes static analyser basic scan.
   - Requirement/design documents and coding standards are available.
   - Code split into manageable parts (2,000 LOC is too large for one
     session; review at 200-400 LOC per hour, so split into 5-6 sessions).

3. PLANNING AND KICK-OFF
   - Moderator selects participants, schedules sessions (max 2 hrs each).
   - Kick-off meeting: author explains purpose, structure and context of the
     module; roles assigned; checklists distributed.

4. INDIVIDUAL PREPARATION
   - Each reviewer reads code independently using the checklist and notes
     defects (rate: about 100-200 LOC/hr).
   - Tools: static analysis (SonarQube, Checkstyle, PMD) to find duplication,
     complexity and naming issues beforehand.
   - Reviewers submit their findings to the moderator before the meeting.

5. REVIEW MEETING (stages)
   a) Opening: moderator confirms preparation was done.
   b) Reader goes through code section by section.
   c) Reviewers raise issues; recorder logs them. No solution discussion
      during the meeting (just identify).
   d) Defects classified and agreed.
   e) Decision: Accept / Accept with minor changes / Re-review needed.

6. DEFECT CLASSIFICATION
   By severity:
     - Major (functional error, security issue, logic fault)
     - Minor (naming, comments, style)
     - Suggestion/improvement
   By type:
     - Naming convention, duplication, complexity, comment, logic, performance,
       security, error handling, standards violation.
   For this module:
     - Inconsistent naming   -> Minor / Standards
     - Duplicated logic      -> Major / Maintainability (candidate for
                                refactoring into functions)
     - Inadequate comments   -> Minor / Documentation
     - Complex conditionals  -> Major / Maintainability and risk of logic
                                errors (check cyclomatic complexity > 10)

7. REVIEW CHECKLIST (sample)
   - Names meaningful and consistent (camelCase/PascalCase as per standard)?
   - Functions short, single purpose?
   - Duplicate code removed (DRY)?
   - Conditionals simplified (nested if, switch, guard clauses)?
   - Cyclomatic complexity within limit?
   - Comments present for non-obvious logic and public methods?
   - Error/exception handling present?
   - Inputs validated?
   - No hard-coded values or unused variables?
   - Resources closed properly?
   - Security issues (SQL injection, secrets)?
   - Matches design and requirements?

8. DOCUMENTATION
   - Defect log (ID, location, description, type, severity, owner, status).
   - Review report: module name, participants, time spent, LOC reviewed,
     number of defects by severity, decision.
   - Metrics: defects per KLOC, review effort (person-hours), review rate.

9. REWORK AND FOLLOW-UP
   - Author fixes all defects (refactor naming, extract duplicate logic into
     functions, simplify conditions, add comments).
   - Moderator verifies fixes (re-inspection if major defects > threshold).
   - Defects marked closed in tracking tool.
   - Exit criteria: all major defects fixed and verified; report signed off.
   - Process improvement: analyse root causes, update coding guidelines,
     arrange training on clean code.

Q4. Explain the difference between peer review and formal review using a
    realistic software project. Assume that five developers are working
    on a large E-Commerce Application. Design a peer-review procedure for
    one critical module and explain how defects should be identified,
    recorded, discussed, corrected, and re-verified.
--------------------------------------------------------------------------
ANSWER:

DIFFERENCE (E-Commerce project with 5 developers)

+----------------+---------------------------+-----------------------------+
| Basis          | Peer Review               | Formal Review (Inspection)  |
+----------------+---------------------------+-----------------------------+
| Formality      | Informal / semi-formal    | Highly structured, defined  |
|                |                           | process                     |
| Participants   | Fellow developers (1-2)   | Moderator, author, reader,  |
|                |                           | scribe, reviewers           |
| Documentation  | Minimal (comments in pull | Complete reports, defect    |
|                | request, checklists)      | logs, metrics               |
| Entry/Exit     | Usually none              | Strictly defined            |
| criteria       |                           |                             |
| Preparation    | Little                    | Mandatory individual prep   |
| Cost/effort    | Low                       | Higher                      |
| Best for       | Everyday code changes     | Critical, high-risk items   |
| Example        | Dev B checks Dev A's      | Formal inspection of the    |
|                | product-search pull       | payment module with         |
|                | request                   | moderator and report        |
+----------------+---------------------------+-----------------------------+

PEER-REVIEW PROCEDURE FOR A CRITICAL MODULE: "Shopping Cart and Checkout"

Team: Dev A (author), Dev B and Dev C (reviewers), Dev D, Dev E.

1. Preparation by author
   - Complete unit tests and self-review; run static analysis.
   - Create a pull request (PR) with a description, linked requirement, and
     changes (small, below 400 LOC).
2. Reviewer assignment
   - Two peers (B and C) are assigned; one must know the payment domain.
3. Defect identification
   - Reviewers read the code using a checklist (logic, validation, security,
     error handling, performance, naming, tests).
   - Check cart total calculation, discount, tax, stock check, concurrency
     (two users buying last item), payment failure handling.
4. Defect recording
   - Comments are added inline in the PR / review tool and each is tagged
     (Major/Minor/Suggestion). Major issues are also logged in the defect
     tracker (ID, location, description, severity).
5. Discussion
   - 30-minute walkthrough meeting or online discussion for disputed points.
   - Focus on the code and not the person. Decisions are recorded in the PR.
6. Correction
   - Dev A fixes defects in new commits and responds to each comment
     (fixed / not an issue with reason).
7. Re-verification
   - Reviewers re-check all fixes; rerun unit/regression tests through CI
     pipeline.
   - Approve PR only when all major issues are closed and CI passes.
8. Closure and metrics
   - Merge code; record review time and defects found; use lessons learned
     to update the checklist.

Q5. A software company has asked its development team to follow strict
    coding standards and guidelines. Prepare a detailed coding-review
    checklist containing at least 20 important criteria related to naming
    conventions, code structure, error handling, security, performance,
    maintainability, comments, exception handling, input validation, and
    resource management. Explain why each criterion is important.
--------------------------------------------------------------------------
ANSWER:

CODING REVIEW CHECKLIST (each item: criterion -> why it matters)

NAMING CONVENTIONS
 1. Variables, methods and classes have meaningful names (e.g.,
    totalAmount, not x).
    -> Makes code self-explanatory and easier to read.
 2. Consistent naming style (camelCase for variables, PascalCase for classes,
    UPPER_CASE for constants).
    -> Consistency reduces confusion and errors.
 3. No misleading or abbreviated names.
    -> Avoids misinterpretation during maintenance.

CODE STRUCTURE
 4. Functions are short and have a single responsibility.
    -> Easier testing, reuse and understanding.
 5. No duplicated code (DRY principle).
    -> A bug fix in one place doesn't need to be repeated several times.
 6. Proper modularisation and separation of concerns (UI/business/data).
    -> Easier changes and parallel development.
 7. Limited nesting and cyclomatic complexity (<= 10).
    -> Complex code is error-prone and hard to test.
 8. No dead/unreachable code or unused variables/imports.
    -> Reduces confusion and clutter.

ERROR AND EXCEPTION HANDLING
 9. All risky operations (file, DB, network) are inside try-catch.
    -> Prevents crashes and data loss.
10. Specific exceptions are caught, not empty or generic catch blocks.
    -> Allows correct recovery and easier debugging.
11. Meaningful error messages and logging, without exposing sensitive data.
    -> Helps support and avoids information leakage.
12. Exceptions are not used for normal flow control.
    -> Maintains performance and clarity.

INPUT VALIDATION
13. All external inputs (forms, APIs, files) are validated for type, length,
    range and format.
    -> Prevents invalid data, crashes and attacks.
14. Validation done on both client and server side.
    -> Client-side checks can be bypassed.

SECURITY
15. Parameterised queries / prepared statements are used.
    -> Prevents SQL injection.
16. No hard-coded passwords, keys or secrets; passwords hashed and salted.
    -> Protects credentials if code or DB leaks.
17. Output is encoded/escaped; authentication and authorisation checks exist.
    -> Prevents XSS and unauthorised access.

PERFORMANCE
18. No unnecessary loops, repeated DB calls or heavy operations inside loops.
    -> Reduces response time and server load.
19. Efficient data structures and algorithms used.
    -> Better scalability.

RESOURCE MANAGEMENT
20. Files, DB connections, streams and sockets are closed (finally /
    try-with-resources).
    -> Prevents memory/resource leaks.
21. Memory allocated is released; large objects are not held unnecessarily.
    -> Avoids memory exhaustion.

COMMENTS AND DOCUMENTATION
22. Comments explain "why" for complex logic; method headers describe purpose,
    parameters, return values.
    -> Helps future developers understand intent.
23. Comments are up to date and not obvious/redundant.
    -> Outdated comments mislead.

MAINTAINABILITY
24. No magic numbers; constants are used.
    -> Easier changes and clarity.
25. Code follows team formatting standard (indentation, line length).
    -> Uniform readability.
26. Unit tests exist for the code and pass.
    -> Safe refactoring and early defect detection.
27. Code matches requirements/design and uses version control properly.
    -> Traceability and accountability.

    five subjects. The system calculates total marks, percentage, grade,
    and pass/fail status. Design a comprehensive Equivalence Partitioning
    strategy for testing this system. Identify valid and invalid
    partitions, boundary-related partitions, representative test data,
    expected results, and explain why your selected test cases are
    sufficient.
--------------------------------------------------------------------------
ANSWER:

ASSUMPTIONS (state clearly in the assignment)
 - Marks per subject are integers 0 to 100.
 - Total = sum of 5 subjects (max 500); Percentage = total / 5.
 - Pass: marks >= 40 in each subject (assumed) and percentage >= 40.
 - Grades: A+ >= 90, A 80-89, B 70-79, C 60-69, D 50-59, E 40-49, F < 40.

 ---|------------------------|-------|-----|-------|--------------------

 - Because the system treats every value in a partition identically, one
   representative per partition gives the same defect detection as testing
   all 101 values, which reduces about 101^5 combinations to a small suite.

Q7. An online shopping application provides the following discount
    rules:
      Purchase below Rs. 1,000        -> No discount

      Rs. 5,000 - Rs. 9,999           -> 10% discount

    Design an extensive set of test cases using Equivalence Partitioning

D. POTENTIAL BOUNDARY DEFECTS AND HOW TESTS EXPOSE THEM
 1. Wrong relational operator: code uses amount > 1000 instead of >= 1000.
    Test 13 (1,000 gets 0% instead of 5%) exposes it. Same for 5,000,
    10,000 and 50,000 (tests 17, 20, 23).
 2. Using >= 999 or > 999 by mistake: Test 11 (999) shows discount wrongly

 6. Data type problems: integer overflow or float rounding (discount on
    1,001 giving 50.05); extreme values (test 25) expose these.
 7. Negative/zero amount accepted: tests 1 and 9.
 8. Rounding errors in discount calculation: check exact computed results.
 9. Discount applied twice or on wrong base: verify final amount values.

Q8. Explain Test to Pass and Test to Fail using a realistic ATM
    withdrawal system. Design separate test scenarios for both
    approaches. Your answer must include normal conditions, invalid
    inputs, boundary conditions, insufficient balance, invalid PIN,
    blocked card, network failure, and transaction timeout situations.
--------------------------------------------------------------------------
ANSWER:

TEST TO PASS (positive testing): verifies that the software works correctly
with valid inputs under normal conditions. Goal: show that the basic
functionality works.

TEST TO FAIL (negative testing): deliberately tries to break the software with
invalid data, extreme conditions and error situations. Goal: find defects
and check that the system handles failures gracefully.

ASSUMED ATM RULES: PIN 4 digits, 3 wrong PIN attempts block the card, min
withdrawal Rs. 100 in multiples of 100, max Rs. 20,000 per transaction, daily
limit Rs. 50,000, timeout 60 seconds of inactivity.

A. TEST TO PASS SCENARIOS
 TC | Scenario                       | Input / Condition        | Expected
 ---|--------------------------------|--------------------------|----------
 P1 | Normal withdrawal              | Valid card, PIN, Rs.2,000, balance 10,000 | Cash dispensed, balance 8,000, receipt printed
 P2 | Minimum amount                 | Rs. 100                  | Cash dispensed
 P3 | Maximum per transaction (boundary)| Rs. 20,000, balance enough | Cash dispensed
 P4 | Balance exactly equals amount  | Balance 5,000, withdraw 5,000 | Success, balance 0 (if no min balance rule)
 P5 | Multiple valid transactions    | 2 withdrawals within daily limit | Both succeed
 P6 | Cancel transaction             | Press Cancel after PIN   | Card returned, no debit
 P7 | Print receipt / SMS alert      | After success            | Receipt and SMS generated

B. TEST TO FAIL SCENARIOS
 TC | Scenario                       | Input / Condition        | Expected
 ---|--------------------------------|--------------------------|----------
 F1 | Invalid PIN                    | Wrong PIN once           | Error message, retry allowed
 F2 | 3 consecutive wrong PINs       | 3 wrong attempts         | Card blocked/retained, message shown
 F3 | Blocked card                   | Insert already blocked card | Transaction refused, message to contact bank
 F4 | Expired / damaged / invalid card | Expired card           | Card rejected
 F5 | Insufficient balance           | Balance 1,000, request 2,000 | "Insufficient funds", no debit
 F6 | Amount not in multiples of 100 | 150, 275                 | Error message
 F7 | Boundary: below minimum        | Rs. 99, 0                | Rejected
 F8 | Boundary: above max            | Rs. 20,100, 20,001       | "Exceeds limit", rejected
 F9 | Daily limit exceeded           | Third Rs. 20,000 withdrawal (total > 50,000) | Rejected
 F10| Negative amount / non-numeric  | -500, "abc", blank       | Rejected
 F11| Network failure during request | Disconnect before bank response | Transaction cancelled, no debit, card returned
 F12| Network failure after debit, before dispensing | Disconnect | Auto-reversal; amount credited back, record logged
 F13| Transaction timeout            | No input for 60 seconds on amount screen | Session ends, card returned/retained safely, no debit
 F14| Cash dispenser failure / out of cash | ATM has no notes   | Error message, no debit or auto reversal
 F15| Power failure / card removed during transaction | Remove card | Transaction aborted safely
 F16| Press keys rapidly / double click Enter | Repeated input  | Only one transaction processed
 F17| Account frozen / closed        | Withdraw                 | Refused

C. WHY BOTH ARE NEEDED
 - Test to pass confirms the system meets requirements in normal use.
 - Test to fail finds hidden defects in error handling, security and
   robustness; for a banking system, wrongly debited money or not blocking a
   stolen card are serious defects.

Q9. A hospital appointment system allows patients to enter their age,
    select a doctor, choose an appointment date, and make an online

Q11. A Food Delivery Application has the following order states:

Q15. Explain the role of static black-box testing in software development.
     Select a realistic requirement document for an online shopping
     system and identify ambiguous, incomplete, contradictory,
     unverifiable, and missing requirements. Prepare a review checklist
     that could be used by a testing team before implementation begins.
--------------------------------------------------------------------------
ANSWER:

ROLE OF STATIC BLACK-BOX TESTING
Static black-box testing means examining the specification (SRS, user stories,
use cases, wireframes) without running any code and without looking at the
code structure. Testers review the document from the user's/external point of
view. Its roles:
 1. Finds defects at the cheapest stage (before design and coding).
 2. Makes requirements clear, complete, consistent and testable.
 3. Prevents wrong assumptions from entering design and code.
 4. Helps testers understand the product and prepare test cases early.
 5. Improves communication among customer, analyst, developer and tester.
 6. Reduces rework and later dynamic-testing effort.

SAMPLE REQUIREMENT DOCUMENT (Online Shopping System - excerpt)
 R1: The system shall allow users to register and log in.
 R2: The website should load quickly.
 R3: Users can add products to the cart and pay online.
 R4: The system shall support most popular payment methods.
 R5: Orders over Rs. 500 get free shipping. (Elsewhere:) R5b: Free shipping is
     available only for orders above Rs. 1,000.
 R6: The system should be user-friendly.
 R7: Users can return products if they are not satisfied.
 R8: The system shall send notifications to users when needed.
 R9: Search should be etc. (incomplete sentence) / Search should show
     relevant products.
 R10: The system must be secure and handle a large number of users.

ANALYSIS OF DEFECTS

 1. AMBIGUOUS
    - R2 "load quickly": how many seconds? Under what load?
    - R4 "most popular payment methods": which ones (UPI, cards, wallet, COD)?
    - R8 "when needed": which events (order placed, shipped, delivered)?
    - R9 "relevant products": what defines relevance?
 2. INCOMPLETE
    - R1: no password rules, mandatory fields, email verification or
      forgot-password flow.
    - R3: no stock check, quantity limits, cart persistence, taxes.
    - R7: return period, conditions and refund process undefined.
 3. CONTRADICTORY
    - R5 vs R5b: free shipping at Rs. 500 versus Rs. 1,000.
    - One section says guest checkout allowed; another says login mandatory.
 4. UNVERIFIABLE / UNTESTABLE
    - R6 "user-friendly", R10 "secure" and "large number of users" cannot be
      measured. Need measurable terms (e.g., "support 10,000 concurrent users
      with response time < 3 s; passwords hashed with bcrypt").
 5. MISSING REQUIREMENTS
    - Order cancellation and tracking; invoice generation.
    - Admin functions (add/edit product, manage inventory).
    - Payment failure and timeout handling.
    - Data privacy, backup and recovery.
    - Browser/device compatibility, accessibility, languages.
    - Coupon/discount handling, wishlist, reviews, address management.
    - Error messages and audit logging.
